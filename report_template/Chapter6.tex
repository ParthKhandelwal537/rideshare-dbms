\chapter{Results and Evaluation}

\section{Verification of CRUD Operations}
\begin{itemize}[itemsep=2pt, topsep=2pt, parsep=0pt]
    \item \textbf{Create (Store):} A rider books a trip from Indiranagar to Airport. PostgreSQL trigger \texttt{trg\_calculate\_fare} queries spatial coordinates ($12.9719^\circ\text{N}, 77.6412^\circ\text{E}$ to $13.1986^\circ\text{N}, 77.7066^\circ\text{E}$), computes the Haversine distance of $28.40\text{ km}$, and evaluates:
    $$\text{Fare} = 50 + (12 \times 28.40) = \text{Rs. } 390.80$$
    Simultaneously, a linked record is created in \texttt{payments} with \texttt{payment\_status = 'pending'}.
    \item \textbf{Retrieve (Read):} Rider dashboard queries \texttt{/api/rides?user\_id=...} utilizing index scan on \texttt{idx\_rides\_user\_id} in under $12\text{ ms}$. Admin Command Center inspects joined \texttt{ride\_full\_details} view in real-time.
    \item \textbf{Update (Modify):} Prior to payment, the rider modifies the dropoff destination to Whitefield. The trigger executes again, recalculating distance ($12.30\text{ km}$) and updating the fare to $\text{Rs. } 197.60$. Clicking 'Pay Now' updates status to \texttt{completed}.
    \item \textbf{Delete (Cancel):} Cancelling an unpaid reservation executes \texttt{DELETE FROM rides}. Because \texttt{payments.ride\_id} is configured with \texttt{ON DELETE CASCADE}, the pending payment is automatically purged without leaving orphaned records.
\end{itemize}

\section{Constraint \& Business Rule Enforcement}
\begin{itemize}[itemsep=2pt, topsep=2pt, parsep=0pt]
    \item \textbf{1:1 Vehicle Ownership:} Attempting to assign a second vehicle to an existing driver triggers a PostgreSQL constraint violation:
    \texttt{ERROR: duplicate key value violates unique constraint 'vehicles\_driver\_id\_key'}.
    \item \textbf{Invoice Lock Integrity (Rule FR7):} Attempting to edit or cancel a paid trip returns HTTP 400 Bad Request: \textit{'This ride cannot be edited or cancelled after payment is completed'}, guaranteeing invoice audit trails.
    \item \textbf{Capacity Bounds:} Passenger count is strictly validated against vehicle seating capacities (Hatchback: 3, Sedan: 4, SUV: 6).
\end{itemize}

\section{Query Performance Evaluation}
As detailed in Table~\ref{tab:benchmarks}, \texttt{EXPLAIN ANALYZE} benchmarks demonstrated that secondary B-Tree indexes on foreign keys accelerated filtered lookups from $2.410\text{ ms}$ (sequential scan) to $0.084\text{ ms}$ (index scan), achieving up to a \textbf{28.7-fold query speedup} under concurrent traffic load.
